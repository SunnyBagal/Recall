The count is all routing needs: is this user at or below the threshold?
- **The btree nearly removed HNSW.** With it present, `enable_seqscan = off` alone makes the planner read the user's rows through the btree and sort them, about 19x slower for the whole-table user. The HNSW route now also turns off bitmap scans and sorts.

## Methodology

- **Dataset:** BEIR SciFact, 5183 documents, the 300 queries in `qrels/test.tsv`. Binary labels. Queries that return nothing score 0 and stay in the averages.
- **Metrics:** k = 10, last timed pass. Rankings changed between passes for 0/0/0 queries (FTS/vector/hybrid) before and 0/0/0 after.
- **Ingestion:** rows inserted as pending, jobs sent through BullMQ on local Redis, unmodified `processContent` with real Haiku and OpenAI calls, cached to disk. `fetchMetadata` is skipped because the corpus has no URLs: title and og_title are the document title, extracted_text is the abstract. The worker ran at concurrency 12 with 6 attempts (production: 3 and 3).
- **Search:** every mode calls `hybridSearch` from `services/searchService.ts`. FTS only passes a null embedding, vector only skips the keyword arm.
- **Latency:** 3 sequential passes over all queries per mode. Before each mode Postgres restarts and a new Bun process starts. Pass 1 is reported as first run, passes 2 and 3 pooled as warm. The connection is opened before timing starts. p50 and p95 are nearest-rank.
- **"First run" is not fully cold.** Postgres shared buffers and the Bun process are cold, but the macOS file cache survives a Postgres restart and clearing it needs sudo.
- **Environment:** Postgres 17.10 (Homebrew), pgvector 0.8.2, shared_buffers 512MB, default hnsw.ef_search 40, HNSW m=16, ef_construction=64, on Apple M1 Pro (10 cores, 16 GB). Loopback connection. A developer laptop, not a production server, so compare the numbers with each other, not with production.
- **Commits:** before `e76d974`, round 1 `16d8f23`, round 2 `124a8c9`. Round 2's only later change is a code comment.
- **Round 2 database:** the same ingested corpus, with the user_id btree added. The user splits for the small and medium users match earlier rounds, except that the rest of the table is further split for the 150, 300, 450 and 600 row users.
- **Train embeddings for tuning:** 807 calls, 15,637 tokens, $0.00 at list price (rounded to the cent).
- **Scale:** 5183 rows. Behaviour at larger sizes is not measured here.

From `recall-backend/`. Needs Homebrew `postgresql@17`, `pgvector` and `redis`. Only `eval/ingest.ts` makes paid API calls, using `OPENAI_API_KEY` and `ANTHROPIC_API_KEY`, and it reuses `eval/cache/` when present.

```bash
eval/local-services.sh start
bun --no-env-file run eval/download.ts
bun run eval/ingest.ts --limit=100   # dry run: token counts for 100 docs
bun run eval/ingest.ts               # full ingest; resets the local eval database
bun --no-env-file run eval/fts-variants.ts

bun run eval/embed-train.ts          # train query embeddings
bun --no-env-file run eval/tune-fusion.ts
bun --no-env-file run eval/run.ts --label=round2
bun --no-env-file run eval/vector-latency.ts --label=round2
bun --no-env-file run eval/hnsw-reachability.ts
bun --no-env-file run eval/report.ts
```

The before and round 1 numbers came from the search code at `e76d974` and `16d8f23`, with no user_id btree. To rerun them, check out those commits and use the commands in that commit's report.
