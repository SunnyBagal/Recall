## What the before numbers show

- **FTS was nearly unusable on natural-language queries.** 285 of 300 test queries returned nothing, because every term had to match.
- **Hybrid had almost nothing to fuse,** so it matched vector only: nDCG@10 0.7209 against 0.7201.
- **Smaller users lost most of their vector results.** A user with 68 rows got 14.18% of the exact top 10, averaging 0.52 rows against 6.38 from an exact search.

## What the after numbers show

- **FTS improved a lot on its own:** nDCG@10 0.0420 to 0.4583, and queries with no results 285 to 2.
- **Hybrid got worse, and this is unresolved.** nDCG@10 0.7209 to 0.6742, Recall@10 0.8549 to 0.8423, MRR@10 0.6866 to 0.6298. Per query against vector only: 38 better, 89 worse. RRF weights both arms equally, and FTS now fills its 10 slots at much lower quality (0.4583 against 0.7201), which is the likely reason: its rows displace good vector rows. This was not tested separately.
- **This does not generalize to every workload.** SciFact queries are natural-language claims, which favour embeddings. Short keyword queries, where AND and OR behave differently, are not represented.
- **Hybrid latency rose:** warm p50 2.81 ms to 8.38 ms, because FTS now ranks real matches instead of mostly returning nothing.

- **The earlier ~64x figure applies only to a user who owns nearly the whole table,** and came from one query on a table twice this size. Here that case is 16.8x. For small users HNSW is slower than a seq scan, because the walk visits many other users' rows.
- **The planner override stays.** Without it the planner picks a seq scan for all four users even with iterative scan on. That is always correct, but costs 45.18 ms for the user who owns the table, and grows with that user's row count. With it, the worst case here is 24.15 ms, for the user with 8 rows, and the walk is capped by hnsw.max_scan_tuples. The cost is real: a small user pays 11.33 ms instead of 1.55 ms.
- **relaxed_order over strict_order:** at about the same latency, for the 68-row user it returned 99.96% of the exact top 10 against 98.22%. This compares against exact search, not relevance labels, so it does not use the test labels.
- **Iterative scan cannot reach every row.** One full walk of the index reached 5127 to 5179 of 5183 rows, depending on the query (5183 across 25 walks, `eval/hnsw-reachability.ts`). The exact fallback covers this when fewer than 10 rows come back. When 10 do come back, a missed row stays missed, which is the remaining gap in the table above.
- **Limits of this measurement:** the table has about 5,000 rows. hnsw.max_scan_tuples (default 20,000) cannot bind at this size, so its effect on larger tables is not measured.

## Methodology

- **Dataset:** BEIR SciFact, 5183 documents, the 300 queries in `qrels/test.tsv`. Binary labels. Queries that return nothing score 0 and stay in the averages.
- **Metrics:** k = 10, last timed pass. Rankings changed between passes for 0/0/0 queries (FTS/vector/hybrid) before and 0/0/0 after.
- **Ingestion:** rows inserted as pending, jobs sent through BullMQ on local Redis, unmodified `processContent` with real Haiku and OpenAI calls, cached to disk. `fetchMetadata` is skipped because the corpus has no URLs: title and og_title are the document title, extracted_text is the abstract. The worker ran at concurrency 12 with 6 attempts (production: 3 and 3).
- **Search:** every mode calls `hybridSearch` from `services/searchService.ts`. FTS only passes a null embedding, vector only skips the keyword arm.
- **Latency:** 3 sequential passes over all queries per mode. Before each mode Postgres restarts and a new Bun process starts. Pass 1 is reported as first run, passes 2 and 3 pooled as warm. The connection is opened before timing starts. p50 and p95 are nearest-rank.
- **"First run" is not fully cold.** Postgres shared buffers and the Bun process are cold, but the macOS file cache survives a Postgres restart and clearing it needs sudo.
- **Environment:** Postgres 17.10 (Homebrew), pgvector 0.8.2, shared_buffers 512MB, default hnsw.ef_search 40, HNSW m=16, ef_construction=64, on Apple M1 Pro (10 cores, 16 GB). Loopback connection. A developer laptop, not a production server, so compare the numbers with each other, not with production.
- **Commits:** before `e76d974`, after `16d8f23`.
- **Scale:** 5183 rows. Behaviour at larger sizes is not measured here.

## Reproduce

From `recall-backend/`. Needs Homebrew `postgresql@17`, `pgvector` and `redis`. Only `eval/ingest.ts` makes paid API calls, using `OPENAI_API_KEY` and `ANTHROPIC_API_KEY`, and it reuses `eval/cache/` when present.

```bash
eval/local-services.sh start
bun --no-env-file run eval/download.ts
bun run eval/ingest.ts --limit=100   # dry run: token counts for 100 docs
bun run eval/ingest.ts               # full ingest; resets the local eval database
bun --no-env-file run eval/fts-variants.ts

git checkout e76d974 -- services/searchService.ts   # before
bun --no-env-file run eval/run.ts --label=before
bun --no-env-file run eval/vector-latency.ts --label=before
git checkout 16d8f23 -- services/searchService.ts    # after
bun --no-env-file run eval/run.ts --label=after
bun --no-env-file run eval/vector-latency.ts --label=after
bun --no-env-file run eval/hnsw-reachability.ts
bun --no-env-file run eval/report.ts
```
